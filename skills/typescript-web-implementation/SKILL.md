# TypeScript Web 交付单元

## 输入

- 阅读当前交付单元上下文、已批准的实施计划、验收标准、技术方案和当前项目约束。
- 已批准计划定义业务目标、验收边界和风险，而不是文件路径白名单。为完成当前工作单元可修改必要的业务代码和测试；任何超出业务目标的重构、依赖升级、凭据或配置变更都必须停止并记录风险。

## 步骤

1. 复用 `superpowers:test-driven-development`，先为每项行为变更建立失败测试，再做最小实现。
2. 遵守项目的依赖版本、代码风格和构建方式；不要无关重构、升级依赖或修改凭据与配置。
3. 在同一次交付内完成代码和工程验证准备；不能把类型检查、构建、关键行为测试或当前验收项留给其他全局节点。测试命令由 AIW 在当前交付运行结束后统一执行并记录真实结果。
4. AIW 运行上下文会在结尾给出“输出回执”。只向其中列出的**暂存路径**写交付报告、验收意图和 Handoff；AIW 会校验全部内容后覆盖当前正式结果。不要自行根据逻辑产物名称推断路径，也不要绕过输出回执写正式任务事实。
5. 交付报告固定包含 `## 实际变更`、`## 工程验证`、`## 测试计划`、`## 逐项验收`、`## 未完成事项与风险`。记录实际修改、测试计划、当前交付单元的每个 AC 的证据与风险；不得伪造退出码、通过/失败结论或测试输出。
6. 仅在输出回执指定的“验收意图”角色中声明当前交付单元的 AC 和业务证据，字段与示例只服从 AIW 当前注入的产物协议。AC 对应的测试能力、测试目标和证据类型已经由批准计划锁定，不得填写测试引用或重新选择测试；真实测试结果和最终验收结论只由 AIW 生成。

## 验证

- 输出回执中要求由 Codex 生成的交付报告与验收意图均存在，且每项实际变更均能关联到当前交付单元目标和验收标准。
- 已给出可由 AIW 实际执行的相关工程验证与测试计划；失败、跳过或无法执行的情况必须在交付报告中如实说明，不能用“后续 verify/test”代替当前结论。
- 不得用计划外的单元测试替代已批准的组件交互、浏览器、契约或集成证据。
- 实际变更均服务于当前工作单元目标与验收标准；不创建、修改或引用输出回执之外的 AIW 任务文件。
