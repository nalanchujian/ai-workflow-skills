# 工作流版本发布指南

## 要解决的问题

本指南面向 `ai-workflow-skills` 的维护者，定义如何升级 `standard-web-feature`、其阶段技能以及整个技能仓库的 Git 发布版本。

用户只选择工作流模板；维护者必须同时管理三层版本：

```text
技能仓库 Git tag：v12.0.1
└─ 工作流模板：standard-web-feature@12.0.1
   └─ 阶段技能：implementation-planning@8.0.1（示例）
```

| 对象 | 记录位置 | 回答的问题 |
|---|---|---|
| 技能仓库 Git tag | Git tag，例如 `v12.0.1` | 用户下载的是哪一个完整技能包快照？ |
| 工作流模板版本 | `profiles/standard-web-feature/PROFILE.yaml` 的 `version` | 任务采用哪一套固定阶段和交付单元流程？ |
| 阶段技能版本 | `skills/<name>/SKILL.md` front matter 的 `version` | 某个阶段实际使用哪一版规则？ |

## 何时升级

### 仅发布 Git tag，模板版本不变

以下改动不改变 `standard-web-feature` 的执行行为：

- 修改 README、示例、注释或许可证说明；
- 新增不被 `standard-web-feature` 引用的模板或技能；
- 修改其他模板的规则。

此时可创建新的 Git tag，例如 `v12.0.2`，但 `standard-web-feature` 仍保持 `12.0.1`。

### 升级阶段技能与模板版本

以下改动改变当前工作流的实际执行行为，必须升级受影响阶段技能和 `standard-web-feature`：

- 改变某阶段的输入、步骤、必需产物或验证要求；
- 改变工作流可执行阶段映射或交付单元语义；
- 升级或替换引用的方法来源；
- 扩大或收紧实现、验证、安全边界。

例如交付单元规则变化时：

1. 修改 `skills/typescript-web-implementation/SKILL.md`，按变更影响提升其 front matter `version`；例如仅新增兼容能力时可从 `5.0.1` 升为 `5.1.0`；
2. 修改 `profiles/standard-web-feature/PROFILE.yaml`：

```yaml
name: standard-web-feature
version: 12.0.1
description: 适用于 TypeScript Web 业务需求的交付单元工作流。
aiwCompatibility: ">=4.0.0 <5.0.0"
artifactContract: aiw.task-output/v1
skills:
  clarify: requirements-clarification@9.0.1
  solution: technical-solution@3.1.0
  plan: implementation-planning@8.0.1
  implement: typescript-web-implementation@5.0.1
```

3. 确认模板引用的每一个 `name@version` 都在同一仓库版本中存在且阶段匹配；
4. 运行 `node scripts/validate-skill-package.mjs`，确认每个技能都声明当前兼容范围和输出契约，且正文没有固化 AIW 任务路径、平台产物文件名、Schema 版本或完整 YAML 示例；
5. 完成审阅与验证后提交，并发布新的 Git tag，例如 `v12.0.1`。

建议遵循语义化版本：修正不改变执行语义的错误用 PATCH；新增兼容能力用 MINOR；移除阶段、改变必需产物或引入不兼容执行方式用 MAJOR。例如将全局 `verify`、`test` 改为每个交付单元自行验证和验收，属于 MAJOR。

## 发布步骤

在 `ai-workflow-skills` 仓库根目录执行：

```bash
git status --short
node scripts/validate-skill-package.mjs
git add skills/ profiles/ method-sources/ README.md docs/
git commit -m "feat: update standard web workflow"
git tag -a v12.0.1 -m "Release standard web workflow 12.0.1"
git push origin main --tags
```

tag 必须指向已审阅、已验证的 commit。不要移动已发布 tag，也不要复用同一个 tag 发布不同内容。

## 用户如何采用新版本

发布后，用户显式执行：

```bash
aiw skills update --ref v12.0.1
```

更新不会自动触发。用户是否采用新版、何时采用新版，应由团队发布策略决定。

更新成功后，`aiw` 会以用户当前默认模板名为锚点，在新技能包中选择同名模板的新版本，并将本机默认 Git tag 与模板引用一并切换。例如旧模板会切换为新包提供的 `standard-web-feature@12.0.1`。新包没有该模板时，用户本机默认配置保持不变。

## 输出契约与兼容性门禁

每个 `SKILL.md` 和 `PROFILE.yaml` 都必须声明：

```yaml
aiwCompatibility: ">=4.0.0 <5.0.0"
artifactContract: aiw.task-output/v1
```

该声明表示技能只兼容当前 AIW 的输出协议。技能正文只能描述方法、输入、所需结果和验证标准；不得出现任务目录、产物目录、交接目录、运行目录、平台产物文件名、Schema 版本、字段白名单或完整 YAML 示例。字段、枚举和示例由 `ai-workflow` 的 Zod Schema 与协议注册表生成；每次运行的物理路径由 AIW 输出回执生成。静态校验与 CLI 安装校验都会拒绝不符合该规则的技能包，避免技能与运行时形成两套协议。

## 升级对进行中任务的影响

当前 `aiw` 的本机技能 Registry 按 Git revision 保留同一来源的多个已安装版本。任务创建时锁定模板、技能、方法来源、Git revision 和内容哈希；后续升级同一技能来源不会替换旧 revision。

因此：

- 用户可以在存在进行中任务时执行 `aiw skills update --ref <new-tag>`；
- 新建任务使用更新后的默认模板版本；
- 进行中的旧任务继续按创建时锁定的 revision 解析技能和方法来源；
- 当前 MVP 不会自动删除旧 revision，也尚未提供技能缓存清理命令。

不要修改已有任务中的版本号来伪造升级。当前任务没有“切换已锁定技能版本”的命令；若必须采用新规则，应从相同需求来源创建新任务，并让旧任务事实留在原业务仓库中供追溯。后续增加缓存清理能力时，必须先检查旧 revision 是否仍被未完成任务引用。
